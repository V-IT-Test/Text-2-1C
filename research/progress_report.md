# Отчёт о ходе работы

**Тема:** «Преобразование естественного языка в язык запросов 1С»
**Дата:** 2026-04-25

---

## 1. Постановка задачи и выбранный подход

Поставленная задача — **Text-to-1C** — представляет собой прямой аналог
известной в литературе задачи **Text-to-SQL** с тем отличием, что целевой
формальный язык — это язык запросов 1С:Предприятие 8.3 (декларативный,
синтаксически близкий к SQL, но русскоязычный, с собственными
конструкциями: виртуальные таблицы регистров, оператор `ЗНАЧЕНИЕ()` для
перечислений, иерархические запросы и т.д.).

Принципиальный выбор подхода — **in-context learning (ICL) поверх готовых
LLM** вместо дообучения собственной модели. Аргументы:

1. **Отсутствие готовых датасетов.** Для Text-to-SQL существуют
   крупные открытые корпуса (Spider, BIRD, WikiSQL, CoSQL), на которых
   можно проводить supervised fine-tuning или RLHF. Для русскоязычного
   языка запросов 1С аналогичных публичных датасетов нет —
   бóльшая часть готовых пар «вопрос → запрос» лежит в закрытых
   корпоративных базах. Сборка датасета достаточного объёма для
   обучения сама по себе является отдельной задачей и выходит
   за рамки текущей работы.

2. **Высокая стоимость и низкая универсальность fine-tuning.** Дообучение
   современной LLM требует значительных вычислительных ресурсов и
   привязывает результат к конкретной конфигурации базы. Любое изменение
   схемы конфигурации 1С (а конфигурации в реальных внедрениях
   отличаются между предприятиями) обесценивает дообученную модель.

3. **Гибкость ICL.** Подход in-context learning позволяет управлять
   поведением модели через системный промпт, подачу схемы, few-shot
   примеры, цепочки рассуждений и постобработку. Это даёт удобный
   инструмент для **ablation study** — основной исследовательской цели
   работы: сравнить вклад различных техник в качество генерации.

Таким образом, в рамках работы **обучения и собственной модели нет**.
Используются готовые LLM, доступные через OpenAI-совместимый прокси
(proxyapi.ru): `gpt-4o-mini`, `gpt-5.4`, `gpt-5.4-mini`, `o4-mini`
(reasoning-модель), `deepseek-v4-pro`, `deepseek-v3`, `deepseek-v4-flash`.
Выбор модели делается из UI на каждый запрос, что позволяет сравнивать
их между собой при одинаковой конфигурации пайплайна.

## 2. Реализованные модули пайплайна

Каркас построен как набор независимо включаемых модулей: пользователь в
UI отдельным тумблером может включить или выключить каждую технику. Это
непосредственно поддерживает дизайн ablation-эксперимента.

### 2.1. Системный промпт с правилами языка запросов 1С

Реализованы **три уровня** системного промпта:

- **Базовый** — короткий, без подробных правил.
- **Продвинутый полный** (~10 КБ) — 21 раздел теории языка запросов:
  ключевые слова, литералы, агрегаты, перечисления (`ЗНАЧЕНИЕ`),
  виртуальные таблицы регистров (`СрезПоследних`, `Остатки`, `Обороты`),
  соединения, шаблоны строк (`ПОДОБНО` с `%`, `_`, `[…]`, `СПЕЦСИМВОЛ`),
  функции дат и строк, иерархия, антипаттерны, восемь развёрнутых
  примеров «запрос пользователя → 1С-код».
- **Продвинутый краткий** (~2 КБ) — сжатая версия для экономии токенов
  и ablation-сравнения «полный vs краткий».

В промпт встроен блок **«Контекст выполнения»** с динамической подстановкой
текущей даты, поскольку в языке запросов 1С отсутствует функция
`ТЕКУЩАЯДАТА()` (она доступна только во встроенном языке) — а параметры
`&X` в нашем сценарии передавать некуда. Дата подставляется как литерал
`ДАТАВРЕМЯ(ГГГГ, М, Д)`.

### 2.2. Загрузка схемы базы (`schema_loader`)

Перед генерацией в LLM подаётся компактная Markdown-схема конкретной
базы: все справочники, документы, регистры, перечисления с типами полей
и синонимами. Получается она в три шага:

1. Запуск `1cv8.exe DESIGNER /DumpConfigToFiles` — выгрузка XML-описания
   конфигурации (~мегабайты).
2. Парсер `schema_compiler2.py` сворачивает XML в Markdown размером
   ~3 КБ — компактный, но сохраняющий все нужные сущности и типы.
3. Кэширование результата в `databases/<key>/DBStructure/schema.md`.

### 2.3. Schema linking (`schema_linker`)

Перед основной генерацией делается дополнительный LLM-вызов, который по
запросу пользователя выбирает только релевантные объекты схемы и
отбрасывает остальные. На больших конфигурациях это сокращает контекст
и убирает шум, мешающий модели выбрать правильную таблицу.

### 2.4. Value-based linking (`value_fetcher`)

После schema linking включается необязательный шаг — обращение **в саму
базу 1С** через COM (без LLM) с запросом нескольких реальных строк из
выбранных справочников/регистров. Эти примеры значений добавляются в
схему. Помогает LLM правильно угадать формат хранения наименований
(например, что сотрудник хранится как «Скоробогатов И.И.», а не просто
«Скоробогатов»).

### 2.5. Chain-of-Thought

Системный промпт расширяется суффиксом, требующим от модели сначала
рассуждать пошагово (какие таблицы, нужны ли срезы, какие условия,
группировка), а финальный запрос вернуть в теге `<query>…</query>`.
Один LLM-вызов.

### 2.6. Query Plan

Двухшаговая стратегия: сначала отдельный LLM-вызов формирует **план
запроса на русском языке** (без кода), затем второй вызов превращает
план в код 1С. Концепция близка к prompt decomposition. Два LLM-вызова.
Взаимоисключающа с CoT (выбор тумблерами через callback).

### 2.7. Critic-агент

После генерации запроса делается дополнительный LLM-вызов с системным
промптом «критика», который проверяет результат по двум осям:

- соответствие запроса намерению пользователя;
- корректность синтаксиса 1С (русские агрегаты, кавычки, `ЗНАЧЕНИЕ`,
  виртуальные таблицы и др.).

Если критик находит замечания, инициируется ещё один вызов LLM с
их учётом, возвращающий исправленный запрос. Срабатывает ВСЕГДА после
генерации, до выполнения — таким образом перехватывает логические
ошибки, не приводящие к ошибкам исполнения.

### 2.8. Execution feedback loop

Сгенерированный запрос автоматически выполняется в реальной 1С через
COM-мост. Если 1С возвращает ошибку — её текст подаётся обратно в LLM
с просьбой исправить. До двух итераций; если за это число попыток
ошибка не исчерпывается, возвращается последний вариант. В отличие
от критика, срабатывает только при наличии runtime-ошибки.

## 3. Подходы, рассмотренные, но не реализованные

В качестве отдельной части ablation-исследования был составлен и
проанализирован полный список 14 техник, применимых к Text-to-SQL/1С
без дообучения. Из них реализовано 8 (см. выше), остальные 6 осознанно
отложены либо отброшены — каждое решение фиксировалось с пояснением.

| Техника | Решение | Причина |
|---|---|---|
| **Few-shot retrieval (DAIL-SQL)** | отложено | требует ручной сборки банка из 50–100 пар «вопрос → запрос». Для тестовой базы — domain-specific (не переносится), для синтаксиса — трудозатратно собрать качественный generic-набор. Имеет смысл вернуться, когда будет время на сборку |
| **Self-consistency / voting** | отброшено | дорого: N LLM-вызовов + N выполнений в 1С на каждый запрос; сложная нормализация результатов для голосования; даёт пользу в основном на нестабильных запросах, которых в нашем тестовом сете меньшинство; execution feedback и critic покрывают большинство ошибок дешевле |
| **DIN-SQL декомпозиция** | отброшено | реальные запросы одновременно попадают в несколько классов сложности (AGGREGATE + JOIN + VIRTUAL); классификация сводится либо к улучшенному SYSTEM_ADVANCED, либо к мультиметке, легко запутывающей модель |
| **QDecomp (декомпозиция на подзапросы)** | отложено как потенциально интересное | концептуально сильная идея, но в 1С жёсткие ограничения на вложенность (`СрезПоследних` не вкладывается в виртуальные таблицы, ограничения на подзапросы в `ИЗ`). Сборка подзапросов в валидный 1С-запрос — отдельная нетривиальная инженерная задача |
| **Hybrid rules + LLM** | отброшено | низкая научная ценность: шаблоны специфичны для конкретной базы, не обобщаются, ablation-выводы несформулируемы. Скорее продуктовая оптимизация, чем исследовательский метод |
| **Clarification + LLM user simulator** | отложено как факультатив | самая высокая научная ценность, но и наибольший объём работы: требует симулятор-пользователя (вторая LLM с ground truth), датасет с эталонными ответами, протокол по типу Bird-Interact. Тянет на отдельную главу — реализуется при наличии времени после основных экспериментов |
| **Grammar-constrained decoding** | отброшено | требует доступа к процессу генерации токенов (локальная модель + GBNF-грамматика). Через OpenAI API / proxyapi.ru недоступно. Упомянуть в работе как направление будущих исследований |

## 4. Структура проекта

```
Text_2_1CQuery/
├── ui/app.py                     — Streamlit-интерфейс
├── pipeline/
│   ├── query_translator.py       — ядро перевода и системные промпты
│   ├── schema_loader.py          — загрузка/кэширование схемы
│   ├── xml_exporter.py           — выгрузка XML из 1С
│   ├── schema_compiler2.py       — XML → компактный Markdown
│   ├── schema_linker.py          — LLM-фильтр объектов схемы
│   ├── value_fetcher.py          — примеры значений из реальной базы
│   ├── critic.py                 — LLM-критик
│   ├── executor.py               — запуск 32-битного COM-моста
│   └── ambiguity_resolver.py     — уточняющие вопросы (в разработке)
├── executor_bridge.py            — 32-битный COM-мост к 1С
├── llm_client.py                 — обёртка OpenAI-клиента
├── config.py                     — список моделей, фиче-флаги
├── research/                     — исследовательские заметки
│   ├── methods_discussion.md     — анализ 14 техник
│   └── progress_report.md        — этот отчёт
├── evolvhist/                    — история форматов схемы
├── databases/<key>/              — конфиг и схема каждой базы
├── README.md                     — инструкция по установке и запуску
└── requirements.txt              — зависимости
```

Архитектурная особенность — **двойное Python-окружение**:
64-битное для UI и LLM, 32-битное для COM-моста к 1С (поскольку
платформа 1С 8.3 предоставляет только 32-битную DLL `comcntr.dll`,
которую 64-битный интерпретатор загрузить не может). Связь между
процессами — JSON через stdin/stdout.

## 6. Текущее состояние и ближайшие планы

- Базовый пайплайн работоспособен: запрос на естественном языке
  переводится в исполняемый запрос на языке 1С и возвращает данные.
- Завершён цикл проектирования всех 14 техник, реализованы 8.
- Системный промпт прошёл итеративную доработку с верификацией каждой
  упоминаемой конструкции (по официальной документации 1С 8.3.20+).

Дальнейшие шаги:
1. **Сборка тестового сета** — вопросы пользователя + эталонные запросы
   1С, для количественной оценки качества.
2. **Метрики** — execution accuracy (совпадение результатов
   выполнения), exact match по нормализованному запросу.
3. **Эксперименты** — попарные сравнения конфигураций пайплайна
   (включая выбор модели LLM) на собранном тестовом сете.
4. **Возврат к отложенным методам** при наличии времени —
   в первую очередь Few-shot retrieval и Clarification dialog.
